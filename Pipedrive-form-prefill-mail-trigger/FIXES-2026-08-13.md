# Pipedrive-form-prefill-mail-trigger — Fixes & Vorschläge

Stand 2026-08-13, Review von `Code.js`. Das Script wird manuell gestartet (kein Trigger,
kein Webhook), deshalb sind die Punkte hier durchgehend niedriger priorisiert als in den
anderen Projekten.

Legende: 🟡 vor Dauerbetrieb · ⚪ Aufräumen

---

## 🟡 P1 — Kein Retry, anders als in allen anderen Scripts

```js
function fetchPipedrive(path) {
  const response = UrlFetchApp.fetch(url, {...});
  if (code !== 200) throw new Error(...);
```
Ein 429 oder ein kurzer 502 lässt den Prefill-Aufbau hart scheitern. Bei Handbetrieb heißt
das "nochmal klicken" — ärgerlich, nicht schlimm. Sobald das Script aber je automatisiert
angestoßen wird (naheliegend: Prefill-Mail beim Stage-Wechsel), gehört der Retry-Wrapper rein.

**Fix:** `callPipedriveWithRetry` aus einem der anderen Projekte übernehmen — oder direkt aus
der geplanten Library.

## 🟡 P2 — `person_id` wird nicht defensiv aufgelöst

```js
const person = fetchPipedrive(`persons/${deal.person_id}`);
```
Das Bundesland-Script macht an derselben Stelle bewusst
`deal.person_id.value || deal.person_id`, weil Pipedrive je nach Endpoint mal eine Zahl und
mal ein Objekt liefert. Kommt hier ein Objekt an, entsteht die URL `persons/[object Object]`
und der Fehler sieht aus wie ein API-Problem.

**Fix:** dieselbe Zeile übernehmen. Einzeiler.

---

## 🟡 P3 — Veraltete Options-Mappings fallen nur im Log auf

`DACHFORM_OPTIONS`, `EINDECKUNG_OPTIONS`, `AUSRICHTUNG_OPTIONS` usw. sind hartcodierte
Options-IDs. `mapOption()` warnt bei einer unbekannten ID —
```js
if (!text) Logger.log(`WARNUNG: Unbekannte Options-ID ${rawId} bei "${feldname}" …`);
return text || '';
```
— und liefert dann leer zurück. Ergebnis: das Feld fehlt im vorbefüllten Formular, der Kunde
bekommt einen unvollständigen Link, und gemerkt hat es niemand, weil die Warnung im
Ausführungsprotokoll steht.

Legt jemand in Pipedrive eine neue Dachform an, tritt genau das ein.

**Fix:** `pruefeKonfiguration()` analog zu den Bundesland-Scripts — gleicht alle sechs
Options-Maps gegen `dealFields` ab. Vorlage: `Montagepartner-aus-Bundesland/Code.js`,
Zeile 276–298 (`pruefeEnumFeld()`), die Funktion ist bereits generisch geschrieben und
funktioniert hier unverändert.

Zusätzlich: einen Zähler zurückgeben, wie viele Felder beim Prefill leer geblieben sind, und
das an den Aufrufer melden statt nur zu loggen.

## ⚪ P4 — `TEST_EMAIL` ist der einzige Schutz vor echtem Mailversand

```js
const TEST_EMAIL = 'valentin@rp-energietechnik.at'; // Solange gesetzt: keine Mail an echte Kunden
```
Das ist derselbe Mechanismus wie `DRY_RUN` in den anderen Projekten, nur anders benannt und
ohne die Sichtbarkeit eines booleschen Schalters. Wer die Zeile leert, verschickt sofort an
Kunden.

**Fix (kosmetisch, aber konsistent):** in `DRY_RUN` / `TEST_MODUS` umbenennen und die
Empfängeradresse separat halten. Dann gilt in allen sechs Projekten dieselbe Konvention und
das Dashboard kann den Modus einheitlich melden.

---

## ⚪ P5 — Adress-Struktur ebenfalls geraten

```js
const adresse = adrObj?.formatted_address || adrObj?.value || '';
```
Gleiche ungeprüfte Annahme wie in `Ordnererstellung-bei-Gewonnen` (dort O6). Anders als dort
gibt es hier keine Warnung, wenn beide Felder leer sind — die Adresse ist dann im Formular
einfach leer.

**Fix:** dieselbe Warnzeile wie in `FolderCreation.gs` ergänzen, damit der Fall im Log auftaucht.

## Beobachtung: das ist der Anfang der Formular-Kette

Laut Projektstand fehlt weiterhin der **Formular-Rückschreib-Agent** (Formular → Pipedrive) —
also die Gegenrichtung zu diesem Script. Der war in der Agenten-Analyse als einziger
"sofort baubar, keine Blocker" eingestuft und existiert noch nicht.

Wenn er gebaut wird, gehört er in ein **eigenes Apps-Script-Projekt**, nicht in dieses:
sonst kollidieren `PIPEDRIVE_DOMAIN`, `fetchPipedrive` und die Feldkonstanten, wie bei allen
anderen Zusammenlegungen auch.
