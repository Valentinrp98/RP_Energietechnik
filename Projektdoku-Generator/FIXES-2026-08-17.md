## P0 — Blocker vor dem ersten scharfen Lauf

### [ ] P0-1 · Doc wird erzeugt, aber Status/Link-Patch kann stillschweigend fehlschlagen → Deal hängt für immer

**Datei:** `DocGeneration.js:115-128`

Zwei Schritte ohne Absicherung dazwischen: erst Doc anlegen, dann `patchPipedrive`. Schlägt der
Patch fehl (Netzfehler, oder — der wahrscheinlichere Fall — die *stille Nicht-Schreibung*, weil das
Status-Feld ein `autocomplete`-Feld ist und den Label-String statt der numerischen Options-ID will),
passiert Folgendes:

1. Doc liegt im Ordner, Status bleibt auf `rdy for creation`, Link-Feld bleibt leer.
2. Nächster Tageslauf findet den Deal wieder, der Duplikat-Schutz (`DocGeneration.js:106`) greift,
   Ergebnis: `SOFT_ERROR` — **aber Status und Link werden nie nachgezogen.**
3. Der Deal produziert ab jetzt jeden Tag dieselbe SOFT_ERROR-Zeile, für immer.

Bei der stillen Nicht-Schreibung antwortet Pipedrive mit **200**, das Script meldet also Erfolg,
obwohl nichts geschrieben wurde (bekanntes Muster, siehe CLAUDE.md).

**Fix, zwei Teile:**

**(a) Patch-Ergebnis verifizieren statt blind vertrauen.** Neue Funktion in `Config.js` neben
`patchPipedrive`:

```js
/**
 * Schreibt custom_fields und prüft an der API-Antwort nach, dass die Werte wirklich angekommen
 * sind. Pipedrive antwortet auch dann mit 200, wenn ein Feld den Wert im falschen Typ bekommt
 * (Options-ID statt Label bei autocomplete-Feldern) und ihn stillschweigend verwirft.
 */
function patchCustomFieldsVerified(dealId, customFields) {
  const data = patchPipedrive(`deals/${dealId}`, { custom_fields: customFields });
  const zurueck = (data && data.custom_fields) || {};
  const nichtAngekommen = Object.keys(customFields).filter(
    key => String(zurueck[key]) !== String(customFields[key])
  );
  if (nichtAngekommen.length > 0) {
    throw new Error(
      `Pipedrive hat ${nichtAngekommen.length} Feld(er) nicht übernommen (200, aber Wert nicht gesetzt): ` +
      nichtAngekommen.map(k => `${k} (gesendet: ${customFields[k]}, zurück: ${zurueck[k]})`).join('; ') +
      ' -- Feldtyp prüfen: autocomplete will das Label als String, single option die numerische ID.'
    );
  }
  return data;
}
```

In `DocGeneration.js:121-126` `patchPipedrive(...)` durch `patchCustomFieldsVerified(deal.id, {...})`
ersetzen. Der Fehler wird dann von `generateDailyProjectDocumentation` als `HARD_ERROR` geloggt,
statt als stiller Erfolg durchzugehen.

**(b) Duplikat-Fall selbstheilend machen.** In `DocGeneration.js:107-109`: wenn ein Doc schon
existiert, aber Status/Link am Deal noch nicht gesetzt sind, nachziehen statt nur skippen.

```js
const vorhandenesDoc = findExistingDoc(projektdokuFolder, kundenName);
if (vorhandenesDoc) {
  const docUrl = vorhandenesDoc.getUrl();
  const linkFehlt = !cf[DOKU_LINK_FIELD_KEY];
  const statusFehlt = String(cf[DOKU_STATUS_FIELD_KEY]) !== String(DOKU_STATUS_OPTION_DONE);
  if ((linkFehlt || statusFehlt) && !DRY_RUN) {
    // Ein früherer Lauf hat das Doc erzeugt, ist aber vor/beim Zurückschreiben gescheitert.
    // Jetzt nachziehen, sonst hängt der Deal für immer im Trigger-Zustand.
    patchCustomFieldsVerified(deal.id, {
      [DOKU_LINK_FIELD_KEY]: docUrl,
      [DOKU_STATUS_FIELD_KEY]: DOKU_STATUS_OPTION_DONE
    });
    return { status: 'OK', docUrl, kunde: kundenName, completeness,
             detail: 'Doc existierte bereits -- Link/Status nachgezogen' };
  }
  return { status: 'SOFT_ERROR', docUrl, kunde: kundenName, completeness,
           detail: 'Doc existiert bereits im Ordner -- kein neues erzeugt (Duplikat-Schutz)' };
}
```

### [ ] P1-1 · Bricht der Lauf ab, geht das komplette Log verloren

**Datei:** `DocGeneration.js:8-31`

`testEinzelDeal()` (`SetupHelper.js:81-83`) macht es bereits richtig mit `finally`. Inkonsistent.

**Fix:** kompletten Rumpf in `try/finally` und Fehler mitloggen:

```js
function generateDailyProjectDocumentation() {
  starteLauf('generateDailyProjectDocumentation');
  const summary = { verarbeitet: 0, uebersprungen: 0, fehler: 0 };
  try {
    const deals = findDealsForDokuErstellung();
    // ... bestehende Schleife ...
    logRow(null, null, null, summary.fehler > 0 ? 'HARD_ERROR' : 'OK', null, null,
```

### [ ] P1-2 · Kein Zeit-Guard — Lauf kann am 6-Minuten-Limit sterben

**Datei:** `DocGeneration.js:15-26`

`findDealsForDokuErstellung()` paginiert über **alle** Deals (bei ~6.500 Deals rund 66 API-Calls),
danach kommt pro Treffer ein `DocumentApp.create()` + `saveAndClose()` — das sind je nach Doc-Größe
mehrere Sekunden. Setzt jemand 40 Deals auf einmal auf „rdy for creation" (realistisch beim
Erstbestand!), reißt der Lauf das Limit.

Weil der Status pro Deal sofort nach dem Doc-Bau geschrieben wird, ist ein Abbruch fachlich
unkritisch — der nächste Lauf macht weiter. Es fehlt nur der geordnete Ausstieg.

**Fix:** in der `forEach`-Schleife (besser: `for…of`, damit `break` geht) vor jedem Deal prüfen:

```js
const MAX_LAUFZEIT_MS = 4.5 * 60 * 1000; // freiwilliger Abbruch vor dem 6-Min-Limit

for (const deal of deals) {
  if (Date.now() - _laufStart > MAX_LAUFZEIT_MS) {
    logRow(null, null, null, 'OK', null, null,
           `Laufzeit-Limit erreicht -- ${deals.length - summary.verarbeitet - summary.uebersprungen - summary.fehler} Deal(s) offen, werden im nächsten Lauf erledigt`);
    break;
  }
  // ... bestehender try/catch-Block ...
}
```

`MAX_LAUFZEIT_MS` als Konstante zu `Config.js` neben `DRY_RUN`.

### [ ] P1-3 · `addFile`/`removeFile` scheitert bei Shared Drives und hinterlässt Waisen-Docs im Drive-Root

**Datei:** `DocGeneration.js:115-118`

```js
const doc = buildProjectDoc(deal, person);
const file = DriveApp.getFileById(doc.getId());
projektdokuFolder.addFile(file);
DriveApp.getRootFolder().removeFile(file);
```

Zwei Probleme:

1. `addFile`/`removeFile` sind veraltet und funktionieren **nicht** mit Shared Drives. Liegen die
   Partner-Ordner (oder werden sie später) in einem Shared Drive, schlägt das fehl.
2. Wirft `addFile` — egal warum —, bleibt das frisch erzeugte Doc im Drive-Root liegen, der
   Pipedrive-Patch passiert nie, und der Duplikat-Schutz sucht im *Zielordner*, findet dort nichts.
   Ergebnis: **jeder Tageslauf legt ein weiteres Waisen-Doc im Root an.**

**Fix:** die moderne, atomare Variante nutzen und den Fehlerfall aufräumen:

```js
const doc = buildProjectDoc(deal, person);
const file = DriveApp.getFileById(doc.getId());
try {
  file.moveTo(projektdokuFolder); // moveTo statt addFile/removeFile: Shared-Drive-tauglich, ein Schritt
} catch (e) {
  // Doc hängt sonst für immer im Drive-Root und wird beim nächsten Lauf erneut erzeugt.
  file.setTrashed(true);
  throw new Error(`Verschieben in "${PROJEKTDOKU_UNTERORDNER_NAME}" fehlgeschlagen (${e.message}) -- leeres Doc wurde in den Papierkorb gelegt`);
}
```

### [ ] P1-4 · Duplikat-Schutz greift auch bei gelöschten Docs

**Datei:** `DocGeneration.js:132-135` (und analog `139-144`)

`folder.getFilesByName()` liefert auch Dateien im **Papierkorb** zurück. Löscht jemand das Doc, um
eine Neuerzeugung auszulösen, findet der Duplikat-Schutz die Papierkorb-Leiche und verweigert —
der Deal ist blockiert, ohne dass im Ordner etwas sichtbar wäre. Diagnose-Albtraum.

**Fix:**

```js
function findExistingDoc(folder, kundenName) {
  const it = folder.getFilesByName(`Projektdokumentation - ${kundenName}`);
  while (it.hasNext()) {
    const f = it.next();
    if (!f.isTrashed()) return f; // getFilesByName liefert auch Papierkorb-Dateien
  }
  return null;
}
```

Gleiches Muster in `findProjektdokuUnterordner()` für `getFoldersByName()`.

### [ ] P1-5 · Unerreichbarer Drive-Ordner wird zum HARD_ERROR statt zum klaren SOFT_ERROR

**Datei:** `DocGeneration.js:138-144`

`DriveApp.getFolderById(match[0])` wirft, wenn der Kundenordner gelöscht wurde oder das
Script-Konto keinen Zugriff hat. Der Fehler landet im generischen `catch` von
`generateDailyProjectDocumentation` als `HARD_ERROR` mit einer nichtssagenden Drive-Meldung —
obwohl es ein Setup-/Berechtigungsproblem ist, kein technisches Versagen des Scripts.

**Fix:**

```js
function findProjektdokuUnterordner(kundenordnerLink) {
  const match = String(kundenordnerLink).match(/[-\w]{25,}/);
  if (!match) return null;
  let kundenordner;
  try {
    kundenordner = DriveApp.getFolderById(match[0]);
  } catch (e) {
    return null; // Ordner gelöscht oder kein Zugriff -- vom Aufrufer als SOFT_ERROR behandelt
  }
  const it = kundenordner.getFoldersByName(PROJEKTDOKU_UNTERORDNER_NAME);
  while (it.hasNext()) { const f = it.next(); if (!f.isTrashed()) return f; }
  return null;
}
```

Zusätzlich in `processDeal` (`DocGeneration.js:95`) die Detail-Meldung ergänzen, dass auch ein
gelöschter/nicht freigegebener Kundenordner diesen Fall auslöst — sonst sucht man am falschen Ende.

### [ ] P1-6 · Vollständigkeits-Metrik ist unbrauchbar, weil Optionalfelder mitzählen

**Datei:** `Config.js:95-121`

`CONTENT_FIELDS` enthält „Interne Notizen" und „Sonstige Mitteilung Kunde" — beides Freitextfelder,
die im Normalfall leer sind. Die Log-Spalte „Befüllt" zeigt dadurch dauerhaft z.B. `12/14`, und
„Leere Felder" listet bei jedem Deal dieselben zwei harmlosen Einträge. Damit verliert genau die
Spalte ihren Signalwert, die man beim Durchsehen des Log-Sheets zuerst anschaut.

**Fix:** Optionalität am Feld markieren und nur Pflichtfelder zählen:

```js
const CONTENT_FIELDS = [
  { key: NETZANSUCHEN_FIELD_KEY, label: 'Netzansuchen' },
  // ...
  { key: NOTIZEN_INTERN_FIELD_KEY, label: 'Interne Notizen', optional: true },
  { key: NOTIZEN_KUNDE_FIELD_KEY, label: 'Sonstige Mitteilung Kunde', optional: true }
];

function checkFieldCompleteness(cf) {
  const istLeer = f => {
    const v = cf[f.key];
    return v === null || v === undefined || v === '' || (Array.isArray(v) && v.length === 0);
  };
  const pflicht = CONTENT_FIELDS.filter(f => !f.optional);
  const leereFelder = pflicht.filter(istLeer).map(f => f.label);
  return { befuellt: pflicht.length - leereFelder.length, gesamt: pflicht.length, leereFelder };
}
```

### [ ] P2-4 · Adresse im Doc-Kopf ohne PLZ, anders als im Ordnernamen

**Datei:** `DocGeneration.js:234-240` vs. `Ordnererstellung-bei-Gewonnen/FolderCreation.gs:63-65`

**Fix:** dieselbe Join-Logik wie im Schwester-Script verwenden:

```js
function formatAdresse(adressFeld, plzFeld) {

    ? (adressFeld.formatted_address || adressFeld.value || '')
    : (adressFeld ? String(adressFeld) : '');

}
```

mit Autocomplete-Adresse anschauen und ggf. nur bei fehlendem `formatted_address` anhängen.

## Nicht gefixt, aber bewusst notiert

**Vollscan über alle Deals pro Lauf.** `findDealsForDokuErstellung()` holt bei ~6.500 Deals rund 66
Seiten, um meist 1–3 Treffer zu finden. Läuft, ist aber verschwenderisch. Die saubere Alternative
wäre `itemSearch/field?entity_type=deal&field={code}&match=exact&return_item_ids=true` — ob das bei
einem Enum-Feld auf die Options-ID matcht, ist **ungeprüft**. Erst an einem Deal verifizieren, dann
umstellen; nicht blind einbauen. Solange P1-2 (Zeit-Guard) drin ist, ist der Vollscan unkritisch.

**Kein `LockService`.** Anders als `Ordnererstellung-bei-Gewonnen` (das per Webhook parallel laufen
kann) hat dieses Script nur einen Tages-Trigger. Ein manuell gestartetes `testEinzelDeal()` während
des Tageslaufs könnte theoretisch kollidieren; der Duplikat-Schutz fängt das fast immer ab. Wenn es
billig ist, `LockService.getScriptLock()` in `generateDailyProjectDocumentation` mitnehmen.

**`checkConfiguration()` läuft nicht automatisch vor dem Massenlauf.** Überlegenswert: am Anfang von
`generateDailyProjectDocumentation` aufrufen und bei Problemen mit `KETTE_BLOCKIERT` abbrechen,
statt einen Lauf mit kaputter Config durchzuziehen. Erst sinnvoll, wenn P0-2 die Prüfung vollständig
gemacht hat.
