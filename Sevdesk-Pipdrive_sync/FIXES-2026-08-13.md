# Sevdesk-Pipedrive-Sync — Fixes & Vorschläge

Stand 2026-08-13, Review von `syncengine.js`. Dieses Projekt ist am nächsten am Live-Betrieb
(15-Minuten-Trigger auf `syncPendingOrders()`), deshalb wiegen die Punkte hier schwerer als
anderswo.

Legende: 🔴 vor Go-Live · 🟡 vor Dauerbetrieb · ⚪ Aufräumen

---

## 🔴 V1 — Der Duplikat-Schutz sprengt irgendwann das Script-Property-Limit

```js
const SYNC_STATE_KEY = 'SYNCED_ORDERS';   // {orderId: updateTimestamp}
saveSyncState(state)  →  props.setProperty(SYNC_STATE_KEY, JSON.stringify(state));
```
Der State wächst **monoton** — jeder je gesyncte Auftrag bleibt für immer drin, nichts wird
je entfernt. Ein einzelner Script-Property-Wert ist auf **9 KB** begrenzt.

Überschlag pro Eintrag: `"123456":"2026-08-13 10:22:11",` ≈ 32 Zeichen
→ **bei etwa 280–290 Aufträgen ist die Grenze erreicht.**

Ab da wirft `setProperty()`. Und zwar am Ende von `syncPendingOrders()`, also **nachdem**
bereits nach Pipedrive geschrieben wurde: die Aufträge sind gesynct, gelten aber weiter als
"nicht gesynct" → beim nächsten Lauf werden sie erneut verarbeitet, wieder geschrieben,
wieder nicht gemerkt. Endlosschleife im 15-Minuten-Takt, die bei jedem Durchlauf Pipedrive
beschreibt.

**Fix — eine von drei Varianten:**
1. **Aufräumen:** Einträge älter als z.B. 90 Tage vor dem Speichern verwerfen (einfachster
   Weg, braucht ein Datum statt nur des Timestamps als Wert)
2. **Auslagern:** State in einen eigenen Tab des Log-Sheets schreiben statt in eine Property
3. **Aufteilen:** auf mehrere Properties verteilen (unschön, verschiebt das Problem nur)

Variante 1 reicht — abgeschlossene Aufträge ändern sich nicht mehr.

**Sofort prüfbar:** einmal `Logger.log(JSON.stringify(getSyncState()).length)` ausführen.
Wenn das über ~7000 liegt, ist die Uhr am Ticken.

## 🔴 V2 — Fehlerhafte Aufträge blockieren die Warteschlange dauerhaft

```js
const batch = zuSyncen.slice(0, MAX_ORDERS_PER_RUN);   // 25
…
if (erfolg) { state[o.id] = o.update || ''; }          // nur bei Erfolg merken
```
Absicht ist richtig (Fehler sollen wiederholt werden), der Effekt ist es nicht: ein Auftrag
ohne passenden Pipedrive-Deal schlägt **jedes Mal** fehl, wird nie gemerkt, steht deshalb
immer wieder ganz vorne in `zuSyncen` und belegt einen der 25 Plätze — für immer.

Bei 25 dauerhaft unzuordenbaren Aufträgen ist der Batch komplett verstopft und **kein einziger
neuer Auftrag** wird je verarbeitet. Im Log sieht das aus wie ein normal laufender Sync mit
ein paar Warnungen.

**Fix:** Fehlversuche zählen und nach z.B. 5 Versuchen parken:
```js
state[o.id] = { ts: o.update, versuche: (alt.versuche || 0) + 1, status: 'FEHLER' };
// beim Filtern: geparkte Einträge überspringen, aber im Log-Sheet als "wartet auf Zuordnung" führen
```
Und diese Zahl gehört ins Dashboard — "12 Aufträge warten seit Tagen auf Zuordnung" ist genau
die Information, die heute niemand hat.

## 🔴 V3 — Kein Retry bei 429/5xx

`pipedriveFetch()` und `sevdeskFetch()` haben **keinen** Retry-Wrapper. Alle vier anderen
RP-Scripts haben einen (`callPipedriveWithRetry`, 3 Versuche, exponentiell). Ausgerechnet das
Script, das alle 15 Minuten läuft und damit als einziges regelmäßig in Rate Limits laufen kann,
hat keinen.

Ein 429 wird hier zu einem harten `throw` → `logSyncResult('ERROR', …)` → Auftrag gilt als
gescheitert → wird beim nächsten Lauf wiederholt (und zählt auf V2 ein).

**Fix:** den bestehenden `callPipedriveWithRetry` aus einem der anderen Projekte übernehmen
(oder, besser, direkt in die geplante Library `RPPipedrive` legen — dieses Script wäre der
erste Nutzer).

## 🟡 V4 — Ein Feld wird ohne `|| null` geschrieben

```js
customFields[FIELD_KEYS.Module_Anzahl] = aggregated.fields.Module_Anzahl;
customFields[FIELD_KEYS.WR_Leistung_kW] = aggregated.fields.WR_Leistung_kW || null;
customFields[FIELD_KEYS.Speicher_Kapazitaet_kWh] = aggregated.fields.Speicher_Kapazitaet_kWh || null;
```
Die erste Zeile ist die Ausnahme. Ist `Module_Anzahl` `undefined`, wirft `JSON.stringify` den
Schlüssel raus, Pipedrive antwortet 200, das Log meldet SUCCESS — und geschrieben wurde nichts.
Genau der Fall, der im Montagepartner-Script als "FIX A" behoben wurde.

Der Kommentar darüber ("Immer aktiv setzen (auch null) — sonst bleiben Werte vom letzten Sync
stehen") beschreibt die Absicht korrekt; die Zeile hält sich nicht daran.

**Fix:** `|| null` bzw. `?? null` ergänzen. Einzeiler.

## 🟡 V5 — Log-Fehler werden verschluckt

```js
} catch (e) {
  Logger.log('⚠️ Konnte nicht ins Sync-Log schreiben: ' + e);
}
```
Wenn das Sheet umbenannt, der Tab `Sync-Log` gelöscht oder die Freigabe geändert wird, läuft
der Sync **weiter** und schreibt weiter nach Pipedrive — nur eben ohne jede Spur. Nach zwei
Wochen fällt niemandem auf, dass es kein Log mehr gibt.

**Fix:** einmal pro Lauf (nicht pro Zeile) prüfen, ob das Log-Sheet erreichbar ist, und bei
Fehlschlag den Lauf abbrechen bzw. ins Dashboard melden. Ein Sync ohne Log ist im Zweifel
schlimmer als kein Sync.

## 🟡 V6 — `getDealCustomFieldValue()` macht einen Extra-Call pro Treffer

Die Gegenprobe Angebotsnummer↔Kundennummer ist fachlich gut (fängt Tippfehler ab), kostet aber
einen zusätzlichen Deal-Abruf pro gematchtem Auftrag. Bei 25 Aufträgen pro Lauf sind das
25 Calls extra — verkraftbar, aber unnötig: `searchDealsByField` liefert bereits Treffer-Objekte,
und ein `deals/{id}` ohne `custom_fields`-Filter hätte beide Felder auf einmal.

⚪ Nur anfassen, wenn ohnehin etwas an der Stelle geändert wird.

## ⚪ V7 — Kein `pruefeKonfiguration()`

Die beiden Bundesland-Scripts haben eine Funktion, die hartcodierte Option-IDs gegen die echte
Pipedrive-API abgleicht. Hier gibt es das nicht, obwohl `ENUM_OPTION_IDS` genauso hartcodiert
ist. `addEnumFieldIfSet()` fängt den Fall zwar ab und loggt eine Warnung — aber setzt das Feld
dann auf `null`, überschreibt also einen möglicherweise korrekten Wert mit leer.

**Fix:** analoge `pruefeKonfiguration()` schreiben (Vorlage steht in
`Montagepartner-aus-Bundesland/Code.js`, Zeile 256–298), einmal vor dem Go-Live laufen lassen
und danach bei jeder Pipedrive-Feldänderung.

---

## ⚪ V8 — Fehlende Retry-Sicherheit bei sevdesk-Pagination

```js
if (offset > 1000) break; // Sicherheitsnetz gegen Endlosschleife
```
Bei mehr als 1000 angenommenen Aufträgen bricht die Schleife still ab — ältere Aufträge werden
dann gar nicht mehr geprüft. Heute weit weg, aber das `break` sollte wenigstens eine Log-Zeile
schreiben, sonst ist es später nicht auffindbar.
